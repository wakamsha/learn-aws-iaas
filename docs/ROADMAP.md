# クラウドインフラ学習ロードマップ

AWS × Terraform によるクラウドインフラ設計・構築の習得計画。
**このファイルには計画だけを書く。** 進捗と決定事項は run ブランチの `docs/PROGRESS.md` に書く。

最終ゴール: **AI Agent に構築を代行させることなく、ネットワーク・コンピュート・DB・監視・CI/CD を備えた Web システムのインフラを、
Terraform で自力で設計・構築・破棄できる。**

## 全体像

| Phase | 作るもの | 中心テーマ | 時間課金 |
| --- | --- | --- | --- |
| 0 | S3 バケット 1 つ | Terraform のライフサイクル / state / plan の読み方 | なし |
| 1 | 静的サイト配信基盤 | リソース間の参照 / リソースベースのポリシー / キャッシュ | ほぼなし |
| 2 | VM ベースの Web システム | VPC / ルーティング / SG / ALB / Auto Scaling / IAM ロール | あり |
| 3 | コンテナベースの Web システム | ECR / ECS on Fargate / RDS / 秘密情報 / module | あり |
| 4 | 運用できるインフラ | リモート state / 環境分離 / 監視 / CI/CD と OIDC | あり |
| 5 | 白紙からの再構築 | 全部を白紙から自力で | あり |

**Phase 1 → 2 の段差が最大。** ネットワークを自分で組み立てるのはここが初めてで、
「plan は通るのに通信できない」という種類の失敗もここで初めて出てくる。Phase 2 を越えると体感速度は上がる。

各 Phase は **新しいディレクトリ(`phaseN-xxx/`)を作って白紙から始める。**
前の Phase のコードを継ぎ足さない。構成を自分で決めること自体が学習対象であり、引き継ぐとその機会が消える。
例外として、Phase 3 では Phase 2 のネットワーク部分を module として移植する(後述)。

---

## Terraform の書き方の段階的導入

Terraform の機能は全 Phase を貫くテーマなので、導入する時期をあらかじめ決めておく。
一度に揃えず、その Phase の主題とぶつからない順に足す。

| Phase | Terraform の書き方 |
| --- | --- |
| 0 | 1 ルートモジュール、ローカル state。`versions.tf` / `providers.tf` / `main.tf` / `outputs.tf` に分ける |
| 1 | リソース間の参照、data source、`aws_iam_policy_document`、provider エイリアス(任意) |
| 2 | `variable` / `locals` / `for_each` / 組み込み関数(`cidrsubnet` など)/ `*.tfvars` |
| 3 | ローカル module(ネットワークを切り出す)、`jsonencode` |
| 4 | S3 backend + ロック、環境ごとのディレクトリ、`tflint`、CI での `fmt` / `validate` / `plan` |
| 5 | 構成ごと自力で組み直す |

### なぜ module を Phase 3 まで入れないか

**切り出す境界は、同じものを 2 回書いて初めて見える。**
Phase 2 でネットワークを 1 回書き、Phase 3 でもう 1 回必要になった時点で、何を入力にし何を出力にすべきかが具体的に分かる。
React のコンポーネントを 1 回目の実装から切り出すと、props の境界をたいてい間違えるのと同じである。

### なぜリモート state を Phase 4 まで入れないか

**リモート state が解決する問題(共有とロック)は、1 人で学習している間は存在しない。**
しかも state を置く S3 バケット自体を Terraform で作るという鶏と卵の問題があり、
state が何であるかを理解する前に入れると、問題の切り分けができなくなる。
Phase 4 で CI から plan を実行する時点で、初めて「ローカル以外から同じ state を読む」必要が生まれる。

## Phase 0: Terraform と AWS の助走

ネットワークは扱わない。AWS と Terraform の操作で迷子にならない状態を作るのが目的。

**終了条件: 1 つのリソースを Terraform で作り・変え・壊し、plan の記号(`+` / `~` / `-/+` / `-`)と state の役割を、自分で説明できる。**

### 進め方

1. 環境構築 — [SETUP-AWS-ACCOUNT.md](./SETUP-AWS-ACCOUNT.md)、[SETUP-TOOLCHAIN.md](./SETUP-TOOLCHAIN.md) を読んで実行する
2. Console で S3 バケットを手で作り、設定項目を眺めてから消す
3. `phase0-hello/` で S3 バケットを Terraform で作る(バージョニング、パブリックアクセスブロック、`default_tags`)
4. `init` が作ったもの(`.terraform/`、`.terraform.lock.hcl`)を確かめる
5. plan を読む → apply → `state list` / `state show` で、自分が書いていない属性を確かめる
6. drift — Console でタグを手で変え、plan で何が起きるかを見る
7. replace — バケット名を変えて plan を読む
8. destroy — オブジェクトが残ったバケットの destroy で何が起きるかを見る
9. 振り返り

### 新しく問われること

- **state とは何か** — Terraform が「このバケットは自分が作った」と覚えている場所。lockfile ではない
- **plan は差分であって、実行結果の保証ではない** — 何が起き得るかを示すだけで、apply が成功するとは限らない
- **変更の種類** — in-place で済むか、作り直しになるか。それを決めているのは誰か(AWS API と provider)

### Console で見るもの

- Console でバケットを作ったときと apply したときに、CloudTrail のイベント履歴に出る API の数と種類の違い

### Phase 0 で意図的に扱わないもの

必要になった Phase で扱う。先回りしても実感が湧かないため。

- IAM のポリシー設計 → Phase 1
- `variable` / `for_each` → Phase 2
- module → Phase 3
- リモート state → Phase 4
- `import` → 必要になったら

## Phase 1: 静的サイト配信基盤

FE エンジニアに身近な「SPA を配信する」を、複数リソースの組み合わせとして組み立てる。

Phase 0 との最大の違いは **リソースが互いを参照すること**。
CloudFront はバケットを、バケットポリシーは CloudFront を参照する。片方だけでは何も配信されない。

### プロダクト側の要求(Tutor が提示する)

社内向けの管理画面(Vite でビルドした SPA)を配信したい。

- HTTPS で配信する
- S3 は直接公開しない
- `/settings/profile` のようなパスを直接開いても表示される
- デプロイしたら利用者にすぐ反映される。ただしアセットはブラウザに長くキャッシュさせたい
- 最低限のセキュリティヘッダーを付ける

学習者はこの要求の過不足を検討してから設計に入る。

**終了条件: 参照し合う複数のリソースからなる配信基盤を、依存関係・権限(リソースベースのポリシー)・キャッシュ戦略を説明できる状態で構築できる。**

### 進め方

1. 要件定義 — 要求の過不足を検討する
2. 構成設計 — リソースの一覧と参照関係、キャッシュ戦略(`index.html` とハッシュ付きアセット)、SPA ルーティングの方式
3. `phase1-static-site/` で S3 / OAC / CloudFront / バケットポリシー / レスポンスヘッダーポリシー
4. ビルド成果物のアップロード(Terraform ではなく `aws s3 sync`。なぜ分けるか)
5. 検証
6. 後片付け
7. 振り返り

### 新しく問われること

- **アイデンティティベースとリソースベースのポリシー** — 「誰が何をできるか」を、主体の側にも資源の側にも書ける
- **グローバルとリージョン** — CloudFront はグローバル、証明書は `us-east-1`、バケットはリージョン
- **長い非同期処理** — CloudFront の作成・削除には時間がかかる。Terraform はその間何をしているか

### 検証で確かめること

- CloudFront 経由で表示され、深いパスを直接開いても表示される
- **S3 のオブジェクト URL に直接アクセスすると拒否される**
- レスポンスヘッダー(`Cache-Control`、キャッシュヒットの有無、セキュリティヘッダー)が設計通り

### Console で見るもの

- ディストリビューションの「デプロイ中」状態の見せ方
- OAC を選んだときに、Console がバケットポリシーの更新をどう案内するか

### Phase 1 で意図的に扱わないもの

- 独自ドメインと ACM 証明書 → ドメインを持っていれば発展課題
- CloudFront Functions / Lambda@Edge
- WAF

## Phase 2: VM ベースの Web システム

VPC から自分で設計し、その上に冗長化された Web サーバーを載せる。

Phase 1 との最大の違いは **通信経路を自分で組み立てること**。
Phase 1 では AWS が用意した経路の上で権限だけを考えればよかったが、
ここではパケットがどのサブネットからどのルートテーブルを見てどこへ出るかを、すべて自分で決める。
そして **plan が通っても通信できるとは限らない。**

### プロダクト側の要求(Tutor が提示する)

Phase 1 の SPA から呼ぶ API サーバーを立てたい(この Phase では nginx が自分のインスタンス ID を返すだけでよい)。

- 1 台が落ちてもサービスが止まらない
- サーバーにはインターネットから直接到達できない
- サーバーに SSH 鍵なしでログインできる(運用者のみ)
- 学習用なので、冗長性とコストのトレードオフは自分で決めてよい。ただし理由を説明できること

**終了条件: VPC から設計した構成に冗長化された Web サーバーを構築し、通信経路を説明でき、
拒否されるべき通信が実際に拒否されることを確かめた状態で、destroy と再構築ができる。**

### 進め方

1. 要件定義
2. 構成設計 — CIDR 設計表、サブネットの役割、ルーティング、SG の通信マトリクス(どこから、どこへ、どのポート)
3. 実装計画 — ファイル分割と、途中で確かめながら進める構築順序
4. `phase2-vm-web/` で VPC / サブネット / ルートテーブル / IGW を作り、Console のリソースマップで確かめる
5. EC2 を 1 台、public subnet に置いて疎通する(user data、IMDSv2、Session Manager、インスタンスプロファイル)
6. NAT Gateway、private subnet への移動
7. Launch Template / Auto Scaling Group / ALB / ターゲットグループ
8. 検証
9. 後片付け
10. 振り返り

**ALB は EC2 単体の疎通を確かめてから積む。** 層が乗った状態で始めると、
失敗の原因がルーティングなのか SG なのかヘルスチェックなのか切り分けられなくなる。

### 新しく問われること

- **public subnet の正体** — サブネットに「public」という設定はない。ルートテーブルが決めている
- **ステートフルとステートレス** — SG と NACL の違いは、戻りのパケットの扱いに出る
- **SG で SG を参照する** — IP ではなく「どの SG を持つ相手か」で許可する
- **IAM ロールと信頼ポリシー** — EC2 がロールを引き受ける仕組み(インスタンスプロファイル)
- **`count` と `for_each`** — 要素を途中から消したときに何が起きるか
- **NAT Gateway のコスト** — AZ ごとに置くか 1 つにするか

### 検証で確かめること

- ALB 経由でアクセスでき、リロードで応答するインスタンスが変わる
- **EC2 にインターネットから直接到達できない**(パブリック IP がない、または SG で拒否される)
- **ALB の SG 以外からの EC2 への通信が拒否される**
- インスタンスを 1 台終了すると、サービスが続き、ASG が補充する
- ALB が返す 502 / 503 / 504 を、それぞれ意図的に起こせる(何を壊すとどれになるか)
- タイムアウトと connection refused の違いから、どこで止まっているかを切り分けられる

### Console で見るもの

- 「VPC など」ウィザードのプレビューが、Terraform の何個のリソースに相当するか(作らずに数える)
- Console で VPC を削除すると依存リソースも消えるが、API の `DeleteVpc` は依存があると失敗する。その差は Console が何をしていることを意味するか

### Phase 2 で意図的に扱わないもの

- HTTPS リスナー(独自ドメインが必要)→ 発展課題
- VPC エンドポイントによる NAT の置き換え → Phase 3 でコンテナと合わせて検討する
- IPv6
- Auto Scaling のスケーリングポリシー → 発展課題

## Phase 3: コンテナベースの Web システム

Phase 2 と同じ「ALB の後ろで冗長化された API」を、コンテナで作り直し、DB を足す。

Phase 2 との最大の違いは **何を自分で管理しなくてよくなり、代わりに何を考えることになったか**。
OS とインスタンスの管理が消える代わりに、タスク定義・2 種類のロール・イメージのタグという新しい概念が出てくる。

### プロダクト側の要求(Tutor が提示する)

API を `app/` の Node.js アプリに置き換え、データを保存できるようにしたい。

- デプロイ単位はコンテナイメージ
- DB はマネージドの PostgreSQL。API からだけ到達できる
- DB のパスワードは誰の手元にも、コードにも残らない
- 新しいバージョンが起動に失敗したら、自動で元に戻る

**終了条件: コンテナと RDB からなる Web システムを、Phase 2 の VM 構成と対応付けて違いを説明でき、
秘密情報がコード・state に平文で残らない状態で構築できる。**

### 進め方

1. 要件定義
2. 構成設計 — Phase 2 との対応表、タスクを置くサブネットの選択(public + パブリック IP / private + NAT / VPC エンドポイント)
3. `phase3-container-web/` を作り、Phase 2 のネットワークを `modules/network` として移植する。
   移植するときに入力と出力を設計し直す(そのままコピーしない)
4. `app/Dockerfile` を自分で書く(非 root、`SIGTERM` で正しく終了する、ターゲットの CPU アーキテクチャ)
5. ECR(イミュータブルなタグ、スキャン、ライフサイクルポリシー)と push
6. ECS クラスター / タスク定義 / サービス / ALB / CloudWatch Logs
7. RDS / サブネットグループ / Secrets Manager によるパスワード管理 / タスクへの秘密の注入
8. デプロイ設定(ローリング更新、サーキットブレーカー)と ECS Exec
9. 検証
10. 後片付け
11. 振り返り

**ECS は DB なしで疎通させてから RDS を足す。** タスクが起動しない原因が、イメージなのかロールなのか DB 接続なのか切り分けられなくなる。

### 新しく問われること

- **タスク実行ロールとタスクロール** — ECS がイメージを取ってくる権限と、アプリが AWS を呼ぶ権限は別
- **`awsvpc` と `target_type = ip`** — タスクごとに ENI を持つことの帰結
- **タグとダイジェスト** — 同じタグが別のイメージを指し得る
- **state に秘密が入る経路** — 変数、output、生成したパスワード。それを避ける手段
- **module の境界** — 何を入力にし、何を出力にするか

### 検証で確かめること

- ALB 経由で `/api/info` が応答し、リロードで hostname が変わる
- **DB に API のタスク以外から到達できない**
- 壊れたイメージをデプロイすると、自動でロールバックされる
- タスクを停止すると、アプリのログに `SIGTERM` の処理が出てから止まる
- タスクの停止理由から、イメージ / 権限 / ポートの不一致を見分けられる

### Console で見るもの

- タスク定義のフォームと JSON の両方の画面と、リビジョンの見せ方
- RDS の「簡単作成」と「標準作成」。何を隠し、何をデフォルトにしているか

### Phase 3 で意図的に扱わないもの

- ECS on EC2(キャパシティプロバイダー)
- ブルー/グリーンデプロイ → 発展課題
- サービスの Auto Scaling → 発展課題
- Lambda などのサーバーレス
- Kubernetes / EKS

## Phase 4: 運用できるインフラ

Phase 3 の構成を、チームで運用できる形に整える。

Phase 3 との最大の違いは **自分以外(CI、別の環境、将来の自分)がこのインフラに触れること**。
ローカルの state、手元からの apply、目視での確認は、ここで通用しなくなる。

### プロダクト側の要求(Tutor が提示する)

- 本番の前に検証用の環境を持ちたい。構成は同じで、規模だけ小さくしたい
- PR を出したら、インフラの変更内容がレビューで見えるようにしたい
- main に merge したら、API の新しいバージョンが自動でデプロイされるようにしたい
- CI に長期のアクセスキーを置かない
- 利用者が「エラーになる」「遅い」と感じる前に気づきたい

**終了条件: リモート state と環境分離を備え、PR で plan、main で API のデプロイが自動で行われ、
利用者影響に気づけるアラームがある状態を、長期アクセスキーなしで構築できる。**

### 進め方

1. 要件定義
2. state 用バケットの bootstrap と S3 backend(ロック付き)
3. `envs/dev` / `envs/stg` の分離
4. CloudWatch アラーム(何を見れば利用者影響に気づけるか)と SNS 通知、ロググループの保持期間
5. GitHub の OIDC プロバイダーと、plan 用・deploy 用のロール
6. PR で `fmt` / `validate` / `plan`、main でイメージのビルド・push・ECS デプロイ
7. タスク定義のイメージ更新を Terraform と CI のどちらが担うかの決定
8. 検証
9. 後片付け
10. 振り返り

### 新しく問われること

- **state の分割単位** — 何を 1 つの state にまとめ、何を分けるか(変更頻度、影響範囲)
- **環境分離の方式** — ディレクトリ / Terraform workspaces / 別アカウント
- **症状のアラームと原因のアラーム** — CPU 使用率は利用者影響を示すか
- **OIDC の信頼ポリシー** — どのリポジトリ・どのブランチ・どのイベントに絞るか
- **インフラとアプリのデプロイの責任分界**

### 検証で確かめること

- 2 つのターミナルから同時に plan / apply しようとすると、ロックで止まる
- **信頼ポリシーで許可していないブランチからのワークフローは、ロールを引き受けられない**
- **plan 用ロールで apply しようとすると拒否される**
- `app/` の `/api/error` / `/api/slow` でアラームが発火し、通知が届く

### Console で見るもの

- CloudWatch のメトリクス画面が、名前空間・メトリクス・ディメンション・統計・期間の多次元の選択をどう表現しているか

### Phase 4 で意図的に扱わないもの

- 複数 AWS アカウント(Organizations)
- CI での自動 apply の本格運用(承認フロー)→ 決定の材料としてのみ扱う
- 分散トレーシング

## Phase 5: 白紙からの再構築

ここまでの知識で、小さな Web サービスのインフラを白紙から自力で設計・構築する。
Phase 1〜4 のコードは見てよいが、コピーしない。

### プロダクト側の要求(Tutor が提示する)

小さな Web サービス(例: メモアプリ)を公開したい。

- SPA は CDN から配信し、同じドメインの `/api/*` を API に振り分ける
- API はコンテナで動き、PostgreSQL にデータを保存する
- 検証用と本番相当の 2 環境(本番相当は apply しなくてよい)
- PR で plan、main で API のデプロイ
- 利用者影響に気づけるアラーム
- 秘密情報はどこにも平文で残らない

**終了条件: 上記を白紙から構築し、構成図・設計判断・コスト見積もり・障害対応と後片付けの手順を文書化し、
destroy → apply → destroy を手順書どおりに再現できる。**

### 進め方

1. 要件定義
2. 構成設計 — 構成図、設計ドキュメント、コスト見積もり(料金ページの数字と確認日)
3. 設計レビュー — Tutor がシニアエンジニアとして設計をレビューする
4. 実装
5. 障害訓練 — Tutor が壊し方を提示し、学習者が実行する。**学習者は何が壊されたかを知らない状態**から、手順書を使って原因を特定する
6. 手順書だけを見て destroy → apply → destroy
7. 振り返り

### Console の設計課題

このシステム一式を Console の 1 つのウィザードで作れるとしたら、どう設計するか。

- ステップ構成と、各ステップで隠すもの・デフォルトにするもの
- 10 分以上かかるリソース(RDS、CloudFront)を含む作成の進捗の見せ方
- 途中で失敗したときの状態の伝え方と、やり直しの UX
- plan のような「実行前の差分」を GUI で見せるなら

ワイヤーフレームと設計理由を残す。これが FE specialist としてのポートフォリオになる。
