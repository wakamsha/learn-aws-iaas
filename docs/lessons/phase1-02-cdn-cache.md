# Phase 1 基礎 単元 2: CDN の用語とキャッシュのヘッダー

Phase 1 では、S3 に置いた SPA を CloudFront(AWS の CDN)から配信する。
この単元では、CDN の用語を覚え、実在のサイトに `curl -I` を送ってキャッシュの動きをヘッダーで観察する。

AWS のリソースは作らない。費用はかからない。

---

## 1. 説明

### CDN がしていること

ブラウザのキャッシュは、FE でおなじみの「一度取ったファイルを手元に取っておく」仕組みである。
CDN は、それと同じことを **利用者とサーバーの間** で、**全利用者で共有して** 行う。

```
ブラウザ ──→ エッジ(CDN の配信拠点) ──→ オリジン(本物のファイルがある場所)
            ここにキャッシュがあれば、         ここまで来るのは
            オリジンへ行かずに返す             キャッシュがないときだけ
```

| 用語 | 意味 | Phase 1 では |
| --- | --- | --- |
| エッジ(POP) | 利用者の近くにある CDN の配信拠点。世界中にある | 東京の利用者は東京近くのエッジにつながる |
| オリジン | 本物のファイルを持っているサーバー | S3 バケット |
| ディストリビューション | CloudFront の配信設定 1 つ分。ドメイン(`xxxx.cloudfront.net`)を 1 つ持つ | Terraform の `aws_cloudfront_distribution` |
| ビヘイビア | パスのパターンごとの設定。「`/assets/*` はこう、それ以外はこう」 | キャッシュのしかたをパスで分ける |
| キャッシュキー | 「同じファイル」とみなす条件。基本は URL。クエリ文字列やヘッダーを含めるかは設定で決まる | |
| TTL | キャッシュを使い続ける時間 | |

### キャッシュは 2 層ある

- **ブラウザのキャッシュ** — その人のブラウザだけが使う
- **CDN のキャッシュ** — エッジにあり、そのエッジにつながる全員で共有する

どちらも、オリジンが返す `Cache-Control` ヘッダーを手がかりにする。

| `Cache-Control` | 意味 |
| --- | --- |
| `max-age=300` | 300 秒間はキャッシュを使ってよい |
| `no-cache` | 使う前に毎回オリジンに「変わっていないか」を確かめる |
| `no-store` | 保存しない |
| `private` | ブラウザには保存してよいが、CDN のような共有キャッシュには保存しない |
| `public` | 共有キャッシュにも保存してよい |
| `immutable` | 期間中は中身が変わらないので、確かめにも行かなくてよい |

CloudFront は、ディストリビューションに設定した「キャッシュポリシー」の範囲内で、オリジンの `Cache-Control` に従う。

### キャッシュの状態が分かるヘッダー

CloudFront は、応答に次のヘッダーを付ける。

| ヘッダー | 意味 |
| --- | --- |
| `x-cache: Hit from cloudfront` | エッジのキャッシュから返した |
| `x-cache: Miss from cloudfront` | キャッシュになく、オリジンから取ってきた |
| `x-cache: RefreshHit from cloudfront` | キャッシュの期限が切れていたのでオリジンに確かめたところ、変わっていなかったのでキャッシュから返した |
| `age` | そのキャッシュがエッジに保存されてから何秒経ったか |
| `x-amz-cf-pop` | 応答したエッジの名前。先頭の 3 文字は近くの空港のコード(`NRT` は成田) |
| `via` | 通ってきた中継サーバー |

## 2. 例題

AWS のドキュメントのトップページは CloudFront から配信されている。2026-10-12 に `curl -I` を送ると、次のヘッダーが返った(抜粋)。

```
Cache-Control: max-age=300, stale-if-error=600
X-Cache: Hit from cloudfront
X-Amz-Cf-Pop: NRT12-P9
Age: 279
```

読み方:

- `max-age=300` → オリジンは「300 秒キャッシュしてよい」と言っている
- `Hit` → 東京のエッジ(`NRT`)のキャッシュから返った。オリジンには行っていない
- `Age: 279` → このキャッシュは 279 秒前に保存された。あと 21 秒で `max-age` に達する

3 秒後にもう一度送ると `Age: 286` になり、同じキャッシュが使われ続けていることが分かった。

同じページに `?x=1` を付けて送ると、`X-Cache: Miss from cloudfront` になった。
このディストリビューションはクエリ文字列をキャッシュキーに含めているので、`/?x=1` は `/` とは別のファイルとして扱われ、まだキャッシュがなかった。

## 3. 練習問題

ターミナルで実際に送って観察する。値は時間とともに変わるので、例題と同じにならなくてよい。

`curl -I` は、本文を取らずにヘッダーだけを表示する。`-s` は進捗表示を消す。

**問 1.** 次を、10 秒ほど空けて 3 回実行する。`x-cache` と `age` はどう変わったか。

```bash
curl -sI https://docs.aws.amazon.com/ | grep -iE '^(cache-control|x-cache|age|x-amz-cf-pop)'
```

**問 2.** 問 1 の `age` が `max-age` の値(300)を超えそうになったら、次の 1 回で何が起きると予想するか。実際に起きたかどうかは見られなくてよい。

**問 3.** クエリ文字列に、自分だけの値を付けて 2 回続けて送る。1 回目と 2 回目の `x-cache` はどうなるか。それはなぜか。

```bash
curl -sI 'https://docs.aws.amazon.com/?learn=任意の英数字' | grep -iE '^(x-cache|age)'
```

**問 4.** 次のサイトも CloudFront から配信されている。2 回続けて送り、`cache-control` と `x-cache` を見る。何度送っても `Hit` にならないとしたら、その理由を `cache-control` の値から説明する。

```bash
curl -sI https://wakamsha.net/ | grep -iE '^(server|cache-control|x-cache|age)'
```

**問 5.** Vite でビルドした SPA には、ファイル名にハッシュが入ったアセット(`assets/index-3f9a2c1b.js`)と、ハッシュが入らない `index.html` がある。
長い `max-age` を付けてよいのはどちらか。理由も 1 行で。

---

## 4. 解答

**問 1.** 多くの場合、3 回とも `Hit` で、`age` は実行の間隔だけ増える。同じエッジの同じキャッシュが使われ続けているからである。途中で `Miss` や `RefreshHit` になったら、キャッシュの期限が切れて取り直したか、別のエッジにつながった可能性がある。

**問 2.** 期限が切れたので、エッジはオリジンに確かめに行く。変わっていなければ `RefreshHit`、取り直したなら `Miss` になり、`age` は 0 付近に戻る(`age` ヘッダーが出ないこともある)。

**問 3.** 1 回目は `Miss`、2 回目は `Hit`。自分だけの値を付けた URL は、まだ誰も取っていない別のキャッシュキーになる。1 回目でエッジに保存され、2 回目はそれが使われる。

**問 4.** `cache-control: private, no-store, no-cache` が付いている。`private` は「共有キャッシュには保存しない」、`no-store` は「保存しない」なので、CloudFront はキャッシュせず、毎回オリジン(`server: AmazonS3`)から取ってくる。CDN を通していても、オリジンのヘッダーがキャッシュさせない指定なら、キャッシュは効かない(キャッシュポリシーの最小 TTL が 0 の場合。最小 TTL を 0 より大きくすると、CloudFront はオリジンの指定より長く保存する)。

**問 5.** ハッシュ付きのアセット。中身が変わるとファイル名(URL)も変わるので、古いキャッシュが使われることがない。`index.html` は中身が変わっても URL が同じなので、長くキャッシュさせると、デプロイ後も古い画面が出続ける。
